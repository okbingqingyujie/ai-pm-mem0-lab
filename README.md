## 2. 是什么：给“下一次对话”准备合适的上下文

Mem0 提供记忆提取、保存、检索与管理能力，可用于需要跨会话延续偏好或任务背景的助手。官方提供开源库、自托管服务及托管平台；本文主要学习开源能力和产品边界。

先区分三种信息来源。这是产品设计上的分工，不是互斥的技术实现：

| 来源 | 回答的问题 | 示例 | 典型风险 |
|---|---|---|---|
| 对话历史 | 刚才说了什么？ | 本轮用户要求“只列三点” | 把临时要求当成长期偏好 |
| 长期记忆 | 之后哪些信息仍有用？ | 用户明确允许记住“解释先给案例” | 过期、误记、跨用户泄露 |
| 业务知识库 / RAG | 业务依据是什么？ | 最新产品手册、公司流程 | 文档失效、权限不当、缺证据 |

记忆系统也可以用检索技术；关键在于来源、作用范围、有效期和控制权。记住用户爱看短答案，不会让助手自动知道公司退款政策。

## 3. 当前能力与边界

### 可以从开源项目学习什么

- 用 `Memory` 接入记忆写入和检索；按用户、Agent、会话等范围组织信息。
- 根据应用选择模型、嵌入模型与存储组件；自托管意味着团队承担配置、运行和数据治理责任。
- 显式读取、更新和删除指定记忆，设计查看与纠错入口。

入门依据：[开源概览](https://docs.mem0.ai/open-source/overview)、[Python Quickstart](https://docs.mem0.ai/open-source/python-quickstart)。默认配置会使用外部模型服务；“自托管存储”不能直接等同“数据完全不出本机”。

### 一个容易沿用旧知识的变化

当前[迁移说明](https://docs.mem0.ai/migration/oss-v2-to-v3)描述的提取流程是 **ADD-only**：新事实可以与旧事实并存，而不是每次写入都自动改写或删除旧记录。这个流程变化不代表显式的 `update`、`delete` 管理操作消失。

因此，“用户改了偏好”至少涉及两个产品问题：新信息是否保存，以及旧信息是否还会影响回答。不能只测试写入成功。显式操作参见[更新](https://docs.mem0.ai/core-concepts/memory-operations/update)与[删除](https://docs.mem0.ai/core-concepts/memory-operations/delete)文档。

### 不要把托管平台功能算到开源库里

[官方比较页](https://docs.mem0.ai/platform/platform-vs-oss)区分了开源与平台能力；例如 Graph Memory、Memory Decay、Temporal Reasoning 和后台整合 Dream 是平台侧能力。开源库的实体匹配不等于拥有完整图记忆或上述时间推理功能。具体版本与接口须再核对。

README 的性能数字来自包含专有优化的托管平台，不能承诺开源部署达到相同成绩。官方页面对“开源是否有 dashboard”的说法也存在范围差异：当前 README 与开源概览介绍自托管服务的 dashboard，比较页仍写未包含。选型时应区分 library 与 server，并核实目标版本，不能把页面摘要直接做成合同承诺。

## 4. AI PM 应先写出的五条规则

以下是本练习建议的产品规则，不是 Mem0 默认保证：

1. **什么可以记**：只保存用户明确同意保留、与学习助手目的相关的信息；一次性格式要求默认只在当前会话生效。
2. **凭什么记**：每条记忆保留来源、主体、时间、适用范围；模型推测不能伪装成用户明确陈述。
3. **谁能取用**：后端根据已认证身份确定用户范围，不信任前端随意提交的用户 ID；仅加一个过滤字段不等于完成授权。
4. **冲突怎么办**：显式纠正优先于旧偏好；时间不明或互相矛盾时，保留不确定性，不强行拼成一个事实。
5. **怎样忘记**：支持查看、纠正、停止新增与删除。停止新增、停止用于回答、删除数据是不同动作，界面需要说清楚。

## 5. 45 分钟练习：设计一个可纠错的学习助手

不必调用模型或注册服务，用表格模拟一次记忆生命周期。以下账号 A、B 和所有发言都是虚构数据。

### 5.1 先画一张记忆卡

为每条候选记忆填写：记录编号、所属用户、原始来源编号、内容、用户是否同意、范围（单轮 / 会话 / 跨会话）、记录时间、有效期、状态（待确认 / 可用 / 已替代 / 不再使用 / 删除待验证）。

这些是产品层字段，不声明全部对应 Mem0 原生字段。持久化方式与后台状态机需要工程实现。展示时只呈现必要信息，不把后台日志或其他用户数据暴露出来。

### 5.2 按顺序走八个场景

| 编号 | 输入或操作 | 应做的事 | 不应发生 |
|---|---|---|---|
| T1 | A：“以后讲概念先给例子，你可以记住。” | 保存跨会话偏好，保留原话来源 | 推断 A 的职业或能力水平 |
| T2 | A：“这次只用一句话。” | 本轮简短回答 | 永久覆盖 T1 |
| T3 | 新会话，A：“解释召回率。” | 召回 T1，先给例子 | 依赖上一轮仍在上下文中才成功 |
| T4 | A：“改一下，以后先给定义，再举例，记住这个。” | 新规则生效，旧规则不再作为当前偏好使用 | 两条相反要求随机命中 |
| T5 | B：“我喜欢怎样的讲解方式？” | 只查 B；没有信息就说明未知 | 返回 A 的偏好 |
| T6 | A：“不要再保存新的学习偏好了。” | 停止此类新增，说明既有记录是否仍使用 | 把“暂停保存”说成“所有历史已删除” |
| T7 | A：“删除你保存的我的讲解偏好。” | 明确目标，执行受授权的精确删除并验证 | 删除 B 或其他类别；仅追加“已删除”文字 |
| T8 | 删除完成后新会话，A：“我喜欢什么讲解顺序？” | 无可用记忆则说明未知；检查旧对话回灌是否重建它 | 从缓存或历史摘要恢复已删偏好 |

T4 可以比较两种实现：只追加新事实，或由产品层将旧记录标为不再使用并控制检索。哪种合适需要真实回归测试；本文不预设 Mem0 能自动满足表中全部行为。

T7 的“删除完成”不能仅凭一次搜索无结果判断，因为搜索可能漏召回。应按记录 ID 核查，再检查用户范围的列表、缓存及应用实际使用的派生副本；原始会话、审计日志和备份的保留政策需分别定义，不承诺它们被一次 API 调用全部清除。

### 5.3 交付与评估

交付：一张记忆状态表、一张八例验收表，以及“查看记忆 / 纠正 / 停止保存 / 删除”的四个低保真交互草图。

以下是练习门槛，不是官方基准或生产通用阈值：

- T1、T3：有明确来源且范围正确；跨会话召回与行为一致。
- T2：单次要求未被错误长期保存。
- T4：重新提问时使用新偏好；另问“以前的要求”时不把历史当当前。
- T5：跨用户检索与输出泄露为 0；测试读取和更改两条路径。
- T6：保存开关关闭后新增记录数为 0；既有记录的使用状态与界面说明一致。
- T7、T8：目标记录和派生使用路径完成核查；未验证项明确标记，不能宣称彻底删除。

用同一组问题比较“无长期记忆”和“有长期记忆”：记录重复询问次数、正确使用偏好的次数、误用旧偏好的次数，以及额外检索成本和延迟。当前表格只写预期，不填写虚构的运行成绩。看过的八例不算独立盲测，正式评估另加未参与调参的新题。

## 6. 学习限制与下一步

- 记忆提取和检索有误差；助手自己的错误陈述可能再次被保存，因此需检查事实来源和可信度，而不是把“助手说过”当完成凭证。
- 隐私合规、安全授权、数据最小化与删除验证是整个产品的责任；接入库或调用删除 API 不能自动证明合规。
- 中文、否定表达、临时偏好和冲突时间线应单独测试；其他数据集的分数不能代替本场景验收。
- 开源免费不等于运行零成本。若以后实做，先固定 SDK 版本，核对迁移变化，使用合成数据验证写入、检索、纠错、删除流程；不要把密钥放进仓库。
- 本仓库仅提供学习整理。没有开通账户、上传真实用户资料、调用付费模型或部署服务，也没有真实产品收益声明。
